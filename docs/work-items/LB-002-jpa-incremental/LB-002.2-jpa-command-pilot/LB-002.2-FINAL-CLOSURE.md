No se afirma que todo JDBC desapareció: los demás commands de `Asistencia`
(`registrarAsistenciaAutonoma`, `solicitarRevisionAsistencia`, `resolverSolicitudRevisionAsistencia`,
`registrarAsistencia`) continúan en JDBC, sin cambio.

## Objetivo

Demostrar que `dbo.usp_registrar_asistencias_sesion` (el único command en alcance de LB-002.2)
puede invocarse desde Infrastructure con JPA (`EntityManager`/`StoredProcedureQuery`) con
comportamiento observable equivalente al baseline JDBC, seleccionable y reversible por Composition
Root, sin cambiar HTTP, Application, Domain, DB ni el SP; y activarlo de forma segura en el perfil
`local`, con validación manual del Golden Path.

## Arquitectura final

```text
Application
    ↓
AsistenciaRepositoryPort
    ↓
Composition Root (selectors independientes: query-provider, command-provider)
    ↓
AsistenciaRepositoryHybridSqlServerAdapter
    ├─ Queries de asistencia          → JPA   (AsistenciaJpaQueryPersistence, vigente desde LB-002.1B)
    ├─ registrarAsistenciasSesion     → JPA   (AsistenciaJpaCommandPersistence → EntityManager.createStoredProcedureQuery
    │                                           → dbo.usp_registrar_asistencias_sesion, mismo SP, binding posicional)
    └─ Demás commands de Asistencia   → JDBC  (AsistenciaRepositorySqlServerAdapter, sin cambio)
```

- Mismo `dbo.usp_registrar_asistencias_sesion`: la firma, el contrato DB, la validación de lote, la
  atomicidad, el mapeo AN/SJC/EX y la clasificación de errores (`DbExceptionTranslator`) no cambian.
- Un solo `EntityManagerFactory`, activo cuando `query=jpa OR command=jpa`
  (`JpaCapabilityRequiredCondition`); sin `JpaTransactionManager`; sin transacción JPA exterior al SP
  (`StoredProcedureQuery` en autocommit, igual que el baseline JDBC).
- Selectores independientes: `asistencia-query-provider` y `asistencia-command-provider`
  (`jdbc|jpa`, default `jdbc`, fail-closed). AS-IS por perfil, verificado contra
  `application.yml`/`application-dev.yml`/`application-local.yml`:

  ```text
  LOCAL:
  query=jpa
  command=jpa

  DEV:
  query=jpa
  command=jdbc

  SIN PERFIL:
  query=jdbc
  command=jdbc
  ```

  `dev` no usa JDBC en ambos selectores: la query ya usa JPA desde LB-002.1B; solo el command
  permanece en JDBC en `dev` (sin cambio, sin dueño de activación en este work item).

## Query JPA (LB-002.0/1/1B)

`AsistenciaJpaQueryPersistence` sobre vistas base (`uv_detalle_asistencia`, `uv_asistencia`,
`uv_estudiante_grupo`), paridad real SQL Server 0 mismatches, N+1 verificado ausente. Activo en
`local`/`dev` desde LB-002.1B (`JPA QUERY ACTIVE: YES`); fallback JDBC disponible
(`APP_ADAPTERS_PERSISTENCE_ASISTENCIA_QUERY_PROVIDER=jdbc`).

## Command JPA (LB-002.2A-E)

`AsistenciaJpaCommandPersistence` (2.2C, GREEN sobre RED congelado) invoca el mismo SP vía
`EntityManager.createStoredProcedureQuery`, binding posicional (4 parámetros:
`idSesion`, `asistenciaJSON`, `idCorrelacion`, `idUsuarioEjecutor`), validado por
`CanonicalProcedureResultValidator` y traducido por el mismo `DbExceptionTranslator` del baseline.
Paridad JDBC↔JPA en SQL Server real (2.2D): `PARITY_MISMATCHES = 0` en todas las comparaciones
JDBC↔JPA aplicables. `COMMAND_PARITY_PROPERTY_TESTS: 27` (21 comparación directa + 3 frontera
transaccional + 3 concurrencia; no las 27 son comparación directa JDBC↔JPA — ver
[PARITY_SNAPSHOT](PARITY_SNAPSHOT.md)), incluyendo AN/SJC/EX con oráculo absoluto, ownership,
matrícula inválida, rollback total, idempotencia, JSON >4000 caracteres, orden de parámetros, fuga
de conexiones y readback campo a campo. `REALTIME_BACKEND_TESTS: 3`
(`AsistenciaCommandRealtimeIT`). `TARGETED_INTEGRATION: 59/59 PASS` (ver
[LB-002.2D-REPORT](LB-002.2D-REPORT.md)). Activado en `local` (2.2E) y validado manualmente contra
SQL Server real y frontend Angular real: Golden Path completo (arranque, autenticación,
`POST /api/v1/asistencias/lote`, persistencia y relectura), sin error de runtime del command JPA.

## SQL Server parity

## Rollback / fallback JDBC preservado

Sin cambios de código: `APP_ADAPTERS_PERSISTENCE_ASISTENCIA_COMMAND_PROVIDER=jdbc` (y
`..._QUERY_PROVIDER=jdbc` para la query) revierten al adapter JDBC baseline, probado en Composition
Root y con evidencia de fail-closed. Los demás commands de `Asistencia`
(`registrarAsistenciaAutonoma`, `solicitarRevisionAsistencia`, `resolverSolicitudRevisionAsistencia`,
`registrarAsistencia`) **no se migraron**: permanecen en JDBC, intencionalmente, sin cambio en el
Composition Root.

  (LB-002.0/1), JPA query activation PASS (LB-002.1B), JPA command pilot PASS (LB-002.2A-C), paridad
  JDBC↔JPA en SQL Server real PASS (LB-002.2D), fallback JDBC preservado, runtime local JPA PASS y
  Golden Path manual PASS (LB-002.2E). No se afirma retiro de JDBC: los demás commands de
  `Asistencia` siguen en JDBC. Ver [TECHNICAL_DEBT](../../../baseline/TECHNICAL_DEBT.md#td-001).
