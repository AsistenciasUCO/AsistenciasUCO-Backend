## Hallazgo durante la fase (clasificación LB-002.2D §34)

Un test inicial (`cmd_par_008_idSesion_null_preserva_la_clasificacion_del_baseline`) falló en su
primera ejecución con la aserción `esApplicationExceptionConocida(jpa)`. Investigación con logging
diagnóstico (`[PARITY-OBS]`) mostró que **tanto JDBC como JPA** lanzan la misma
`DatabaseOperationException` (una `TechnicalException`, jerarquía distinta de `ApplicationException`)
para `idSesion=null` — un UUID null no tiene tipo SQL inferible sin conversión previa, y ambos caminos
delegan esa conversión de forma idéntica. **Clasificación: `TEST_DEFECT`** (la aserción del test
exigía incorrectamente que el resultado fuera una `ApplicationException` de negocio, cuando el propio
baseline JDBC — el oráculo — tampoco lo es). Corrección: el test ahora reconoce como "excepción
controlada" tanto `ApplicationException` como `TechnicalException` (ambas expuestas por
`getCode()`), preservando el requisito real: nunca una excepción cruda del driver sin traducir. **No
se modificó ningún archivo de producción para esta corrección** — la investigación confirmó que la
clasificación productiva (JDBC y JPA idénticas) ya era correcta.
