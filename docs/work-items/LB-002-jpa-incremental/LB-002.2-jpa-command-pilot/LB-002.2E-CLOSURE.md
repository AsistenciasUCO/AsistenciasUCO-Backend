## Resultado

DONE. La activación en runtime local (`asistencia-query-provider=jpa`,
`asistencia-command-provider=jpa`) fue validada manualmente por el usuario contra SQL Server real
(`gestionasistenciadb`) y frontend Angular real: arranque correcto, autenticación, registro de
asistencias (`POST /api/v1/asistencias/lote`), persistencia y relectura correctos, sin error de
runtime del command JPA. Una sesión de revisión humana posterior (mismo día, mismo entorno) validó
además el escenario realtime pendiente: dos clientes SSE recibiendo la actualización y reconexión
tras pérdida/recuperación de conectividad, con reconvergencia observada de aproximadamente 25
segundos y HTTP como fuente de verdad. No se afirma reconexión instantánea. Evidencia completa en
[LB-002.2E-E2E](LB-002.2E-E2E.md).

## Alcance entregado y decisiones

- `application-local.yml`: `asistencia-command-provider` con default
  `${APP_ADAPTERS_PERSISTENCE_ASISTENCIA_COMMAND_PROVIDER:jpa}` (además del
  `asistencia-query-provider=jpa` vigente desde LB-002.1B).
- `.env.example`: comentario actualizado documentando que `local=jpa`, `dev`/sin perfil siguen en
  `jdbc`, y que la variable de entorno sigue siendo el rollback explícito.
- `AsistenciaCommandProviderCompositionRootTest`: `CMD_CFG_011` se separó para caracterizar el nuevo
  AS-IS (`CMD_CFG_011_perfil_local_activa_el_command_jpa`) sin modificar el rollback (`CMD_CFG_012`,
  sigue en verde).
- Validación manual E2E realizada por el usuario (no automatizada, no reproducida por el agente):
  Golden Path de asistencia completo en `local` con JPA en query y en command.
