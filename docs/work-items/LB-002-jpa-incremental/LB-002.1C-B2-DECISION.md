## 1. Requirement (REQUIREMENT aprobado que esta decisión fija)

> Un **operador institucional** (COORDINADOR o ADMINISTRADOR) registra a una persona como estudiante de un grupo indicando su identidad
> completa (tipo y número de documento, nombres, correo y credencial inicial). El sistema garantiza, como una sola operación de
> negocio, que existan `Usuario` + `Estudiante` + `EstudiantePrograma` (programa del grupo) + `EstudianteGrupo` activo, y después
> provisiona la cuenta en el proveedor de identidad. Un estudiante **no** se auto-matricula con esta capability.

Fuentes que sostienen el requirement (no una sola): `SecurityConfig` + [runtime-security-provider-architecture](../../security/runtime-security-provider-architecture.md) §10-11
(`POST /api/v1/grupos/** → COORDINADOR|ADMINISTRADOR`, normativo activo); DB `backend_specification.md` PR-003 (ADMINISTRADOR) y PR-092
(COORDINADOR); DB `usp_registrar_docente_en_grupo` (hermano exacto, ejecutor COORDINADOR); el test DB de ese hermano usa un ejecutor
coordinador; el DB `REPORT` 1C-A declara que "el operador de la spec (COORDINADOR) es rechazado" por el SP de estudiante.

```text

                            Sin InstitutionalScopePort en esta microfase (paridad con crearGrupo/registrarDocenteEnGrupo, ver "Alcance institucional").

                            (DB audit §4.3) pero NO un contrato aprobado para esta familia: se registra como SECURITY_GAP, no se inventa aquí.
```

**Por qué no B (auto-matrícula):** (1) el request trae datos personales completos + password de una persona que *puede no existir todavía*; un usuario inexistente no puede ser el ejecutor autenticado. (2) Con el RBAC `ESTUDIANTE` actual, *cualquier* estudiante activo podría matricular a *cualquier* persona (el propio DB REPORT lo señala); ese es un defecto de copia del SP hermano de docente, no un requisito. (3) La auto-matrícula tiene superficie propia (`/api/v1/estudiante/matricular-grupo`, `solicitudes-matricula`) y modelo pendiente (`SolicitudMatricula` no existe). (4) El texto legacy "auto-registro" describe el flujo de matrícula por QR/PIN, capability distinta.

**Por qué no la DB "solo porque existe" ni el backend "solo porque existe":** ninguna de las dos fuentes por sí sola. El requirement sale de la convergencia de matriz de seguridad normativa + spec PR-003/PR-092 + SP hermano; la DB actual contradice a todas ellas y a su propio hermano.

## 6. DECISIÓN 3 — Usuario existente

```text
MATCHING POLICY:   ambas claves — correo normalizado y (tipo, número) — se resuelven contra Usuario.
  - ninguna existe                         → CREATE Usuario nuevo (con password recibido) + perfil Estudiante
  - ambas existen y son el MISMO Usuario   → REUSE (sin modificar Usuario)
  - alguna existe y la otra no, o existen en Usuarios DISTINTOS
                                           → CONFLICT / REJECT (sin escrituras). No hay merge automático (no existe evidencia que lo autorice).
CONFLICT DBCODES:  documento ocupado por otro correo → ERR_UNICIDAD_DOCUMENTO;  correo ocupado por otro documento → ERR_UNICIDAD_CORREO
                   (ambos ya seeded y ya definidos como ErrorDefinition CONFLICT en el backend; el pre-check backend ERR_IDENTIDAD_USUARIO_CONFLICTO se conserva como ruta rápida, pero NO es atómico: la DB debe imponer la regla)
UPDATE NAMES/CORREO: NO. La matrícula no muta datos personales de un usuario existente (el operador no es titular de esa identidad; ni DB actual ni backend actual lo hacen).
PASSWORD:          se persiste solo al crear. Para usuario existente, el password recibido se ignora (backend ya envía null); no se pisa credencial.
ESTUDIANTE:        se reutiliza el perfil Estudiante existente; se crea solo si falta.
IDENTITY:          la cuenta IdP se provisiona por el use case con el usuario canónico resuelto por (tipo, número) — coherente porque la regla anterior garantiza que ambas claves identifican al mismo Usuario.
```

Justificación de "coherencia total o rechazo": hoy la DB reutiliza por correo ignorando un documento distinto y el backend luego resuelve por (tipo, número), lo que produce un fallo **posterior al commit DB** (matrícula persistida, sin cuenta IdP, sin compensación por diseño: B1 §8-R1). Exigir que ambas claves coincidan elimina esa clase de estado sin inventar un merge. La DB ya rechaza uno de los dos casos parciales (`ERR_UNICIDAD_DOCUMENTO`), de modo que la regla extiende un criterio existente en lugar de crear uno nuevo. **Punto a validar con el equipo DB** en la microfase: que un usuario preexistente con el documento correcto pero un correo *escrito distinto* debe corregirse por el flujo de usuarios, no por matrícula.

## 7. DECISIÓN 4 — Ownership transaccional

```text
OPTION SELECTED:   C — responsabilidades separadas
DB OWNS:           la atomicidad SQL de la operación compuesta Usuario + Estudiante + EstudiantePrograma + EstudianteGrupo: todo o nada, sin Usuario/Estudiante huérfanos,
                   tanto si el SP corre solo (otros consumidores/tests) como si se une a una transacción externa (savepoint, sin commit/rollback total de la externa;
                   patrón ya probado para el hermano: test_transaction_ownership.sql OWNERSHIP_STUDENT/docente con "savepoint rollback parcial").
BACKEND OWNS:      (a) el límite de transacción de la llamada (TransactionOperations sigue envolviendo el command y hace rollback si el traductor lanza) como defensa en profundidad,
                   NO como único garante; (b) el orden DB-first y no invocar Identity antes del commit DB.
NOT ACID:          SQL transaction ≠ Keycloak transaction. Identity ocurre DESPUÉS del commit DB; no existe transacción distribuida.
EXPECTED BEHAVIOUR ON POST-COMMIT IDENTITY FAILURE:
                   la matrícula DB permanece (no se deshace); el use case responde error controlado (InternalApplicationException, ya así hoy) y el estado
                   "matriculado sin cuenta IdP" es un estado conocido y reintentable, NO un bug silencioso. No se diseña saga ni compensación aquí (fuera de alcance de B2).
```

Razón de no A ni B puros: la DB no puede cubrir Keycloak, y el backend no puede garantizar atomicidad *dentro* de un SP que otros consumidores/tests también invocan; el backend solo no basta (B1 §6: la fila de ownership es `NOT CERTIFIED` en DB) y la spec DB exige "atomicidad requerida" para esta transacción (`especificacion_sp_endpoints.md` Transacción 3.1). El hecho de que `TransactionOperations` exista hoy no decide la responsabilidad. La certificación del ownership DB requiere un test DB con **escritura intermedia real seguida de fallo** (brecha señalada en 1C-A §7).
